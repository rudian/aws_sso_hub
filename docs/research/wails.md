## 1. Decision: Wails **v3.1.0**

Pin all three pieces to the same version:

| Piece | Exact pin |
|---|---|
| CLI | `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.1.0` |
| Go module | `github.com/wailsapp/wails/v3 v3.1.0` in `go.mod` |
| JS runtime | `"@wailsio/runtime": "3.1.0"` in `frontend/package.json`. Use the exact version, no `^`. |

D1 stands. v3.1.0 is a real stable release, and it cross-compiled a Windows amd64 `.exe` on this arm64 Mac without Docker.

### 1.2 Why v3 and not v2

- v3 has a **system tray with menus that can change at runtime** (P1 menu-bar/tray login). v2 has no tray API.
- v3 bindings are generated by static analysis. You get typed TS interfaces, TS enums from Go consts, typed custom events, and doc comments. Calls are **cancellable**: a `context.Context` parameter is cancelled when JS calls `.cancel()`. This suits a long SSO login wait.
- v3 has a built-in single-instance lock with a callback, manager APIs (`app.Dialog`, `app.Browser`, `app.Clipboard`, `app.Event`, `app.SystemTray`) and a Taskfile build you can read and edit.
- On both versions the Windows build is pure Go (no CGO, no Docker), so the cross-compile requirement does not favour either one.

### 1.3 Risks of v3.1.0 and how to handle them

| Risk | Mitigation |
|---|---|
| v3.1.0 is 3 days old and v3 now ships weekly. Many PRs in 3.1.0 were authored by a bot account (`taliesin-ai`). | Pin exact versions (table above). Do not run `wails3 update`. Upgrade only on purpose, and update all three pins together. |
| Open issue #6378 (open, reported on v3.0.0): on **Windows** the tray icon sometimes does not appear (`ShellNotifyIcon NIM_ADD failed`). | Treat the tray as optional (P1). **Default: closing the main window quits the app.** Offer "keep running in tray/menu bar" as an opt-in setting. Otherwise a missing tray leaves a hidden window that cannot be reached. |
| Open issue #6368 (reported on beta.34): on Windows, `OnShutdown` is not called when the last window is closed with X. | Do not rely on `OnShutdown` for anything important. Write files atomically when you save them. Stop the loopback OIDC listener when its flow finishes, not at shutdown. |
| Open issue #6375: on Windows a teardown race in `Quit()` together with a **third-party** systray library. | Do not add third-party tray libraries. Use only `app.SystemTray`. |
| Windows runtime behaviour could not be checked here (WebView2, tray, dialogs, console windows). | **Early milestone:** run a Windows smoke test (VM or a teammate) of the spike build before building features. See the checklist in section 6. |

### 2.3 Docker, CGO and Go 1.27 (VERIFIED, from the generated Taskfiles and the runs)

- **No Docker** is needed for any target we ship:
  - macOS builds run `build:native` on a darwin host.
  - Windows builds use `CGO_ENABLED=0` and native Go cross-compilation (`build/windows/Taskfile.yml` → `build:native`).
  - Docker (`wails-cross` image) is used only for macOS-from-non-Mac or Windows-with-CGO. We need neither.
- **CGO on macOS**: `CGO_ENABLED=1` plus Xcode Command Line Tools (clang). Both amd64 and arm64 objects build natively on Apple Silicon with Apple clang, so no extra toolchain is needed for `GOARCH=amd64`.
- **CGO on Windows**: not used (`CGO_ENABLED=0`).
- An experimental CGO-free macOS backend exists (`EXTRA_TAGS=purego`). **Do not use it** (experimental in 3.1.0).
- **Go 1.27.3 works.** One fix is needed. Go 1.27 objects target macOS 13.0, but the template links for 12.0, which caused `ld: warning: object file (...go.o) was built for newer 'macOS' version (13.0) than being linked (12.0)`. Fix applied and verified (the warning disappeared):
  - `build/darwin/Taskfile.yml`: set `CGO_CFLAGS`/`CGO_LDFLAGS` to `-mmacosx-version-min=13.0` and `MACOSX_DEPLOYMENT_TARGET` to `"13.0"`.
  - `build/darwin/Info.plist` and `Info.dev.plist`: set `LSMinimumSystemVersion` to `13.0.0`.
  - The app therefore supports **macOS 13 Ventura and newer**.

### 2.5 Generated bindings (VERIFIED with the spike's Go types)

Spike module `awsssohub`, service `AccountService` in package `awsssohub/internal/app`. Generated files:

```
frontend/bindings/awsssohub/internal/app/accountservice.ts   // one exported function per exported method
frontend/bindings/awsssohub/internal/app/index.ts            // export * as AccountService; enums; export type {models}
frontend/bindings/awsssohub/internal/app/models.ts           // interfaces + enums
frontend/bindings/events/index.ts                            // const AuthStatus = "auth:status" ...
frontend/bindings/github.com/wailsapp/wails/v3/internal/eventdata.d.ts   // typed CustomEvents map
frontend/bindings/github.com/wailsapp/wails/v3/internal/eventcreate.ts
```

The type mapping is in the cheat sheet §4. Highlights: Go slices become `T[] | null`, maps become `{ [_ in string]?: V } | null`, `*T` becomes `T | null`, `time.Time` becomes `string`, and multiple results become a tuple. `omitempty` makes the field optional. A `context.Context` first parameter is hidden from TS. String/int const groups become TS `enum`s with an extra `$zero` member. A Go type that no bound method uses in its signature is **not** generated (`AppError` was missing).

### 2.6 End-to-end probe inside the packaged macOS app (VERIFIED)

Production `.app` built and launched. The frontend called a bound `Ping` method that appended lines to a scratch file:

```

mode:isWails=true accounts=1
fail:true:plain failure:cause={}
apperr:{"code":"E_NOT_FOUND","message":"profile not found"}
```

What this shows:
- Runtime detection works in WKWebView: `window.webkit.messageHandlers.external.postMessage` is a function, so `isWails` is true.
- Tuple return works.

- A custom error struct with JSON tags reaches JS as `cause` = its JSON.
- `app.Event.Emit("auth:status", LoginStatus{...})` reaches `Events.On(...)` with typed `ev.data`.
- Single instance: a second launch exited at once with code 0 while the first kept running (RSS about 148 MB).
- Not seen visually: the tray icon and the dialogs. They compiled, and the app ran without crashing with a tray created.

## 4. Locating `aws` and `git`, and the child-process environment

### 4.1 macOS

- **Finder/Dock-launched apps get launchd's PATH**: `/usr/bin:/bin:/usr/sbin:/sbin`. This is well-known Apple behaviour. `launchctl getenv PATH` is empty on this machine, so launchd's default applies. Not reproduced directly: `open bin/X.app` from a terminal **inherits the shell's environment** (`man open`: "Opened applications inherit environment variables..."), and VERIFIED that the app then saw the full shell PATH. Testing from a terminal therefore hides this bug. Test with `env -i` or by double-clicking in Finder.
- On this machine `aws` = `/opt/homebrew/bin/aws` → Cellar 2.39.3, and `git` = `/opt/homebrew/bin/git` (2.56.0). `/usr/bin/git` is the Apple shim (2.54.0, "Apple Git-157"). **The shim opens an "install Command Line Tools" dialog if the CLT are missing**, so check `xcode-select -p` before you call `/usr/bin/git`.
- Login-shell PATH capture (VERIFIED on this machine):
  - `zsh -l -c` took 0.05 s. The PATH contained `/opt/homebrew/bin`, but **after** `/usr/bin`, because this user runs `brew shellenv` from `.zshrc` (interactive), not from `.zprofile`.
  - `zsh -i -l -c` took 1.9 s and gave 26 entries. Interactive rc files may print text; wrap the value in markers.
- **Rule** (implemented and unit-tested in the spike, `internal/execx`; code in cheat sheet §12):
  - Order: preferred dirs `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, then the login-shell PATH (`$SHELL -l -c`, 3 s timeout, markers), then the inherited PATH, then `/usr/bin:/bin:/usr/sbin:/sbin`.
  - With `PATH=/usr/bin:/bin:/usr/sbin:/sbin` (simulated Finder launch) this resolved `aws` → `/opt/homebrew/bin/aws` and `git` → `/opt/homebrew/bin/git` (2.56.0).
  - Show the resolved paths in Environment Check, and allow overrides in Settings.
- Every child process gets `PATH=<that list>`. This matters because git runs the `aws` credential helper through `sh`, and that shell inherits our PATH. The git-codecommit research also recommends an **absolute, quoted aws path in the helper**, so terminal and IDE use does not depend on PATH either.
- Also set for child processes:
  - `AWS_PAGER=` (empty, so the AWS CLI never opens a pager)
  - `GIT_TERMINAL_PROMPT=0` (git never prompts on a TTY)
  - `GCM_INTERACTIVE=never` (Git Credential Manager on Windows)
  - `LC_ALL`/`LANG` left unchanged

### 4.2 Windows (all UNVERIFIED: no Windows machine)

- Typical locations:
  - `aws.exe`: `C:\Program Files\Amazon\AWSCLIV2\aws.exe` (official MSI).
  - `git.exe`: `C:\Program Files\Git\cmd\git.exe` (Git for Windows / winget); per-user install `%LOCALAPPDATA%\Programs\Git\cmd\git.exe`; Scoop `%USERPROFILE%\scoop\shims\git.exe`.
  - GUI apps on Windows inherit the full user and system PATH, so the problem is smaller than on macOS. Still add the known dirs.
- **Hide console windows.** The app is linked with `-H windowsgui` (Taskfile), so any console program it starts (`git.exe`, `aws.exe`) would open a console window. Use `cmd.SysProcAttr = &syscall.SysProcAttr{HideWindow: true, CreationFlags: 0x08000000 /* CREATE_NO_WINDOW */}`. This compiled for `GOOS=windows` (VERIFIED).
  - Open question (UNVERIFIED): when `git` (started with no console) launches the `aws` credential helper, Windows may give `aws.exe` a new **visible** console, because a console child of a console-less parent gets its own console.
  - If the Windows smoke test shows a flashing window during `git ls-remote`/`clone`, start **git** with `HideWindow: true, CreationFlags: 0x00000010 /* CREATE_NEW_CONSOLE */`. That gives git a hidden console that its children inherit.
- **WebView2 runtime**: it is preinstalled on Windows 11 and is normally present on Windows 10 through Edge updates. Wails calls `GetAvailableCoreWebView2BrowserVersionString`; if that fails it logs an error and the window cannot render (SOURCE: `webview_window_windows.go`; the user-visible result is UNVERIFIED).
  - The portable `.exe` relies on the runtime being present. The NSIS installer (later) bundles `MicrosoftEdgeWebview2Setup.exe` and installs it.
  - WebView2 user data defaults to `%APPDATA%\<exe name>`. **Set `Windows.WebviewUserDataPath`** explicitly (cheat sheet §3) so renaming the exe does not move the data.
- Git for Windows ships a system `credential.helper=manager`. The local "reset" (empty helper) from D4 neutralises it. The details are in the git-codecommit research.

## 5. Distribution without code signing

### 5.1 macOS packaging

- The Taskfile ad-hoc signs the bundle: `codesign --force --deep --sign -`. An Apple Silicon binary must carry at least an ad-hoc signature to run.
- The bundle is named after `APP_NAME` (`aws-sso-hub.app`). Rename it to `AWS SSO Hub.app` with `ditto` at release time; the signature stays valid (VERIFIED).
- Zip it with `ditto -c -k --keepParent` (keeps bundle metadata). Do not use `zip -r`.

### 5.2 Windows packaging

- Ship `aws-sso-hub.exe` (portable) zipped.
- NSIS installer later: `brew install makensis` (needs the user's permission), then `wails3 package GOOS=windows GOARCH=amd64 INSTALL_SCOPE=user`. Output: `bin/aws-sso-hub-amd64-installer.exe`. With `INSTALL_SCOPE=user` the install dir is `$LOCALAPPDATA\Programs\<ProductName>` and no admin rights are needed (SOURCE: `build/windows/nsis/project.nsi`).
- Add `build/windows/nsis/MicrosoftEdgeWebview2Setup.exe` (1.7 MB, generated) to `.gitignore`.

### 5.3 Gatekeeper (macOS, unsigned and not notarized)

`spctl` says `rejected` (VERIFIED). A zip downloaded through a browser, AirDrop or chat gets `com.apple.quarantine`, and the first launch is blocked. User workaround for the tutorial (the exact UI wording on macOS 27 is UNVERIFIED):
1. Move `AWS SSO Hub.app` to `/Applications`.
2. Run in Terminal: `xattr -dr com.apple.quarantine "/Applications/AWS SSO Hub.app"`. Then open it normally.
3. Alternative: try to open it once, then go to System Settings → Privacy & Security → "Open Anyway". Since macOS 15, Control-click → Open no longer bypasses Gatekeeper.

Proper fix later: Developer ID signing and notarization (`wails3 tool sign --notarize`, set up via `wails3 setup`).

### 5.4 SmartScreen (Windows, unsigned)

The first run of a downloaded unsigned exe shows "Windows protected your PC". Workarounds:
- Click "More info" → "Run anyway".
- Or before the first run: right-click → Properties → tick "Unblock", or in PowerShell `Unblock-File .\aws-sso-hub.exe`.

Proper fix later: an Authenticode certificate (`wails3 tool sign`).

### 5.5 iCloud-synced project folders

If `~/Documents` is synced (iCloud "Desktop & Documents"), `wails3 tool prepare-macos-output` finds the File Provider and **moves the build output**. `bin/` becomes a symlink into `~/Library/Application Support/Wails/build-output/...` (override with `WAILS_MACOS_OUTPUT_ROOT`). The first build in a fresh `bin/` also spends about 2.5 s probing (SOURCE: `internal/commands/tool_prepare_macos_output.go`). Do not be surprised if `bin` is a symlink.
